## 定位 `dsh web` 启动失败：harness 版本与 Connection API 不匹配

**症状**：`dsh plugin --profile web add file:D:/soft/dsh-desktop/dsh-plugin-code/dsh-proxy` 成功，
随后 `dsh web` 抛
`Error: dsh: plugin tree failed to load: failed to apply loader entry dsh-proxy (@stack-brain/dsh-proxy): Cannot read properties of undefined (reading 'register')`
栈顶指向 `@stack-brain/dsh-proxy/dsh-proxy/lib/index.cjs:4217`。

**根因**：不是代码 bug，是 **harness 版本落后于插件目标版本**。
- 插件（根包 0.2.0 / 子包 0.1.1，分支 `v0.2.0`）用 09-20 合并进来的新版 Connection API：
  `ctx.connection.fetch.register({path, methods, requestBody, fetch})`（`src/index.ts:236`）
  以及 `ctx.connection.authenticatedUrl(...)`（`src/index.ts:218`）。
  这两个 API 由 `@deepseek-ai/dsh-client-connection@0.1.5-rc.2` 的 `HostConnectionHandle` 提供。
- 命令行走的是 nvm 全局 CLI：`D:/develop-tools/nvm-tools/nvm/v24.20.0/node_modules/@deepseek-ai/dsh@0.1.1-rc.2`
  （2026-08-21 发布），其内置 `dsh-client-connection@0.1.1-rc.2` 的 `ctx.connection` **只有** `rpc.{handle,intercept}`，
  没有 `fetch` 注册表、也没有 `authenticatedUrl` → `ctx.connection.fetch` 为 `undefined`，`.register` 直接炸。

**版本矩阵（实测）**：

| 位置 | 版本 | `connection.fetch` | `connection.authenticatedUrl` |
| --- | --- | --- | --- |
| 全局 CLI `dsh`（nvm v24.20.0） | dsh 0.1.1-rc.2 | 无 | 无 |
| 桌面端 `D:\soft\dsh-desktop\DSH Desktop\resources\app` | dsh 0.1.5-rc.2 | 有 | 有 |
| npm latest / next | dsh 0.1.5-rc.2 | 有 | 有 |
| 插件 devDeps 目标 | dsh-* 0.1.5-rc.2 | — | — |

即：**插件 + 桌面端一致（都是 0.1.5-rc.2），只有全局 CLI 是旧的**。
CLI 与桌面端的 profile 也不同：CLI 用 `~/.dsh/profiles/web`（已装 proxy/config-manager/notification-center），
桌面端用 `~/.dsh/profiles/desktop`（bundles 只有 dsh-base + dsh-web-app，未装本插件）。

**已执行的修复**：升级全局 harness，插件代码一行未动。
1. `npm i -g @deepseek-ai/dsh@0.1.5-rc.2`（用 `D:/develop-tools/nvm-tools/nvm/v24.20.0/npm.cmd`，
   让 prefix 落在 nvm 那个版本目录，否则会装到别的 node 版本下）。
2. 连带必须升级 `dsh-config-manager`：`0.1.54` 里 `import { settingsNamespace } from '@deepseek-ai/dsh-settings'`，
   而 0.1.5-rc.2 的 dsh-settings 只导出 `SettingsProvider / SettingsConflictError / redactSecrets / default`
   → 报 `does not provide an export named 'settingsNamespace'`。实测 **0.1.55 起已修**，装到 0.1.61。
   升级命令：`node <dsh>/lib/bin.js plugin --profile web add dsh-config-manager@0.1.61`
   （`dsh plugin --profile <x> ...` 实际就是转发给 profile 目录里的 pnpm）。
   `@lyhalal/dsh-notification-center@0.1.34` 的 settings 导入本来就是 OK 的，无需动。
3. 验证通过：`dsh web` 打印 `dshVersion: 0.1.5-rc.2` 并正常起服，无插件树报错；
   `127.0.0.1:3080` → HTTP 401（浏览器认证页），`127.0.0.1:3081` → OPEN（dsh-proxy 自己的转发端口已起）。

`ctx.connection.rpc.handle` 的旧代码，且旧 harness 完全没有浏览器会话/cookie 体系，

## 双版本兼容可行性调研（只调研，未改代码）

用户问"能不能兼容 0.1.1-rc.2 老 harness"，遂把插件的真实 harness 耦合面量化出来。

**结论：耦合面极窄，双版本兼容技术上完全可行，成本集中在一个"路由适配垫片"上。**

**运行时耦合面（实测，不是推测）**：
- `dsh-proxy/lib/index.cjs` 的 `require()` 只有 Node 内置模块（assert/fs/http/https/net/crypto/os/path/zlib/stream/tty/url/util）
  —— schemastery、http-proxy、dsh-home-paths 都被 esbuild 内联，**零 harness 运行时 import**。
- `dsh-proxy/lib/client.js` 的运行时外部依赖只有 `react` / `react/jsx-runtime`；
  所有 `@deepseek-ai/*` 都是 `import type`，已被擦除（`dsh-client-runtime` 在产物里 0 命中）。
- 因此插件对 harness 的依赖只有 4 个"服务调用点"，全部来自 cordis 注入，不是 import。

**compat matrix（0.1.1-rc.2 vs 0.1.5-rc.2）**：

| 耦合点 | 0.1.1-rc.2 | 0.1.5-rc.2 | 影响 | 现状 |
| --- | --- | --- | --- | --- |
| `ctx.connection.fetch.register({path,methods,requestBody,fetch})` | ❌ 无（只有 `rpc.{handle,intercept}`） | ✅ | **硬失败**：`undefined.register` 崩启动 | 本次故障根因 |
| `ctx.connection.authenticatedUrl(origin)` | ❌ 无 | ✅ | 软降级 | `proxy.ts:201` 已判 `undefined`，`proxy.ts:217` 已 try/catch → 自动退化为"上游 401 原样透传" |
| `ctx.webServer.register({kind,path,handler(req,res)})` | ✅ | ✅ | **无差异** | 两代 `WebRoute` 定义逐字节相同，`() => void` 同步 disposer，都有 `get port()` |
| `ctx.logger` / `ctx.effect` / `ctx.get` | ✅ cordis 4.0.1 | ✅ cordis 4.0.1 | 无 | 稳定 |
| `dsh.client.inject` 里的 `@deepseek-ai/dsh-client-runtime` | 存在 | **已移除** | **无影响**（已核实） | 见下方更正：`inject` 只是信息性元数据，删不删都不会炸 |
| `dsh-client-connection/invariant` 子路径导出 | ✅ 有 | ❌ 已删（0.1.5 exports 只有 `.`/`./client`/`./src/*`） | 若引用需自己实现 | 插件没引用 |
| `dsh-settings` 导出 | 有 `settingsNamespace` | 已删 | 只影响 config-manager | 插件没引用 |
| `cordis.patch.yml` 里 `id: directory-picker / disabled: true` | 通过 | 通过 | 无 | 0.1.1 那次崩溃发生在 apply 阶段 ⇒ patch 阶段已过 |

**可行方案（评估过 4 条，建议 A）**：
- **A（推荐）宿主侧"路由适配垫片"**：新增 `src/connection-bridge.ts`，把"挂一个 `POST /api/dsh-proxy` JSON 路由"
  抽象成一个函数，内部特性探测：`typeof ctx.connection?.fetch?.register === 'function'`
  → 有则走 Connection（自带 Host/Origin 栅栏 + 浏览器会话校验）；
  → 无则 `ctx.webServer.register({kind:'exact', path:'/api/dsh-proxy', handler})`，自己补栅栏。
  **客户端零改动**（`transport.ts` 已是对 `/api/dsh-proxy` 的裸 fetch，两代同一套 wire contract）。
  必须自己写 node:http ↔ fetch 的桥（0.1.1 的 `bridge()` 是包内私有、0.1.5 也没导出），约 60-80 行。
  ⚠️ 降级路径的栅栏必须复刻 0.1.1 的 `authority:'loopback'` 语义（等价 `isTrustedApiRequest(req, [])`：
  查 `sec-fetch-site` 不是 cross-site + Host 必须是 loopback），否则 LAN 上任何人可改代理配置 = **安全回归**。
- **B 宿主侧双实现（走 `rpc.handle`）**：能复用 harness 现成桥和栅栏，但 **wire contract 变了**
  （RPC 信封 `{type:'client-request', rpcId, method, payload}`，端点 channel-relative），
  客户端也得跟着分支（老 `client/index.ts` 用 `ctx.get('connection').rpc.call(...)`），
  且客户端两代 `connection` Context 成员会撞。**不推荐**：宿主省事但把差异扩散到浏览器侧。
- **C 不兼容，留 fork 分支**：老代码完整留在 `_merge-backup`，单开 `v0.1.x-legacy` 分支维护，主线只跟 0.1.5+。
  成本最低、风险最小，老版本不再获得新特性。适合"只为兼容某台还跑 0.1.1 的机器"。
- **D 只加"最低版本"守卫**（与 A/B/C 都不冲突）：
  在 `apply()` 开头加能力探测 + 带版本号的友好报错，替代现在这种"某处 undefined.register"的崩溃；
  顺手删掉 `dsh.client.inject` 里已不存在的 `dsh-client-runtime`（整洁度，非必须）；
  在 AGENTS.md 写清支持的 harness 范围。

**✅ 重要更正（后续核实）**：`dsh.client.inject` **不是**模块解析依据。
`@deepseek-ai/dsh-package-manifest/lib/types/types.d.ts` 的 `DshClientManifest` 明确定义：
- `inject?: string[]` — "Informational package-name dependencies, not Cordis service injection."（纯信息性）
- `external?: string[]` — "Exact module-table requests beyond the implicit client baseline... Type-only imports
  are erased and create no module request." ← **这个才是真正驱动客户端模块表的字段**
所以列一个 harness 里已不存在的包（如 `dsh-client-runtime`）**不会导致运行时失败**，只是元数据陈旧。
此前记忆里"属隐患/定时炸弹"的说法是错的，已作废。本插件没声明 `external`，而它的 client 产物只需要
`react`（属于 baseline externals），所以客户端模块表这块本来就是干净的。

**harness 不提供插件侧的版本约束机制**：`DshManifest` 只有 `bundle` / `profile` / `client` / `configTrees` /
`sessionFormatMigration` / `moduleFallback` 六个角色，**没有 `engines` 或 harness 版本区间字段**；
在 0.1.5 的 239 个包里也扫不到任何"校验插件与 harness 版本匹配"的逻辑。
⇒ "最低版本"只能靠 `apply()` 里自己探测 + 报错，或者靠 `package.json` 的 `peerDependencies`
（`dsh plugin add` 时 pnpm 会打 `[WARN] Issues with peer dependencies found`，但只是 warning，不阻断）。

**注意与仓库既有策略的冲突**：`AGENTS.md:30` 现写的是"When the harness version moves, bump these to the new
harness's bundled versions and re-run pnpm install to fix API drift"——即"跟随单一 harness 版本"。
引入双版本兼容需要改写这条策略，并明确 devDeps 只钉 0.1.5 类型、老版本路径只能用结构化的
`unknown` + 类型守卫表达（tsc 不会替我们检查 0.1.1 那一侧）。

**复现老版本要注意**：本机 0.1.1-rc.2 已被升级覆盖，要回归验证需临时装
（`npm i -g @deepseek-ai/dsh@0.1.1-rc.2`），建议用 nvm 另开一个 node 版本隔离，别污染当前可用的 0.1.5 环境；
且升级/降级 harness 后 `dsh-config-manager` 需跟着切版本（0.1.5 → ≥0.1.55，0.1.1 → 0.1.54）。
